## Setup

- node2vec (torch_geometric + torch-cluster) on each split's input graph only: dimension 128, walk length 20, context 10, 10 walks per node, 1 epoch(s), batch 256, lr 0.05, 1 negative sample.
- Val/test embeddings are rotated into the train embedding's space (orthogonal Procrustes on authors with co-authors in both graphs) so a classifier fitted on train pairs applies. `node2vec_cosine` uses raw within-split cosine similarity and needs no alignment.
- **Chosen on validation:** p = 2, q = 2, operator **l1**, negative mix hard fraction 0, 1:3 (mix by the Phase 4 rule; p, q, operator by val pooled hard_active ROC-AUC). This is the reported node2vec result.
- LightGBM + node2vec: base model `lightgbm_pair_focused` (better on val pooled hard_active; the retrained distance-2 pair-focused model when it is chosen), same settings (num_leaves 3, lr 0.03, min_child 300), plus the 128 l1 dimensions and the raw cosine.

### diagnostic_all_vs_hard

> **Warning — diagnostic only, not a result.** All hard negatives are at distance 2, while 34–41% of positives are at distance ≥ 3, so in this comparison distance alone separates the classes. A learned model that picks up distance (or anything correlated with it) can look good here for the wrong reason; neighbourhood heuristics are pushed the other way, because they score every distance-3+ positive 0, below every hard negative. Neither direction says anything about the task. Use `hard` instead.
